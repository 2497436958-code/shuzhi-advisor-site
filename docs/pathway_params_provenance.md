## 1. 为什么要有这份文件

生成这 6 份预计算样例的脚本已经丢失，但脚本里存着一张「路径级参数表」：

- 每个路径的投入区间（`cost_range`）；
- 每个路径 × 成效采集项的成效弹性区间（`elasticity`）。

后端实时推理层要用这张参数表做 ROI 复算。现有的 `src/` 只实现了判据层打分器
（`advisor.scoring.engine`），诊断 / 路径 / ROI 排序仍是 `reasoning_status = pending`
（见 `docs/backend_api.md`），所以这张表必须从预计算结果里**机械还原**。

还原脚本：`scripts/extract_pathway_params.py`（仅标准库，只读 `precomputed/`，只写 `data/pathways.json`）。

## 3. 还原口径

### 3.1 数学关系（已对 31 条 ranking 行全部验算通过）

```text
benefit_low  = Σ( benefit_bases[采集项] × elasticity[采集项].low  )
benefit_high = Σ( benefit_bases[采集项] × elasticity[采集项].high )
roi_low      = benefit_low  ÷ cost_range[1]     # 悲观下界：最小收益 ÷ 最大成本
roi_high     = benefit_high ÷ cost_range[0]
```

### 3.2 取整规则（容易踩错的一处）

| 量 | 展示精度 | 用哪个值算 |
|---|---|---|
| `benefit_range` | 1 位小数 | 先求和，再四舍五入 |
| `roi_low` / `roi_high` | 4 位小数 | **用未取整的收益值**参与除法 |

反例（P-MES，采集项 13 + 15，投入 60—180 万）：

```text
未取整收益：72×1% + 3600×1% = 36.72   → benefit_low 展示 36.7
  用 36.72 ÷ 180 = 0.204    ← 样例原值 0.204  ✅
  用 36.7  ÷ 180 = 0.2039   ✗ 与样例不符
未取整收益：72×3% + 3600×2.5% = 92.16 → benefit_high 展示 92.2
  用 92.16 ÷ 60 = 1.536     ← 样例原值 1.536  ✅
```

另外「逐个采集项先取整再求和」在 6 个样例上与「先求和再取整」结果完全相同
（如 P-NET 高位：2.2 + 2.2 = 4.4 = round(4.41, 1)），两种口径对当前样例不可区分；
后端接入时按 3.1 的写法（先求和再取整）即可。

### 3.3 弹性区间的解析与三重交叉验算

`pathway[].expected[].expect` 文案形如：

```text
改善 1.0%—3.0%（收益基数约 72.0 万元/年，预期年化收益 0.7—2.2 万元）
改善 0.1%—0.3%（收益基数约 3600.0 万元/年，预期年化收益 3.6—10.8 万元）；该弹性未被公开案例支撑，只用于排序，不作为结论数
```

脚本从文案里取三组数，逐一互校（任一不符立即报错退出）：

| 来源 | 校验对象 | 判据 |
|---|---|---|
| `改善 a%—b%` | `elasticity.low / high` | 直接取值（a/100、b/100） |
| `收益基数约 X 万元/年` | `benefit_bases[采集项]` | 必须完全相等（容差 1e-9） |
| `预期年化收益 A—B 万元` | `base × 弹性` | `round(base×区间, 1)` 必须与文案一致（容差 0.05） |

`supported` 标记：`expected[].supported` 字段与文案里的「该弹性未被公开案例支撑」
必须同时出现或同时不出现，不一致即报错；`supported=false` 的条目原样保留标记。

### 3.4 `depends_on` 的映射

`pathway[].depends_on` 存的是**步骤序号**（1 起，指向同一份 `pathway` 数组内的位置），
还原时映射成该位置上步骤的 `path_ref`。

例：`ap3` 第 4 步 PATH-014 的 `depends_on = [2, 3]`，第 2 步是 PATH-006、第 3 步是 PATH-007，
故 `depends_on_paths = ["PATH-006", "PATH-007"]`。

语义自洽性佐证：6 个样例共 13 条依赖边，依赖目标只落在 3 条路径上——
PATH-008（设备入网与数据采集，9 次）、PATH-006（生产管控，3 次）、PATH-007（质量管理，1 次），
全部符合业务依赖关系（能耗 / 质量 / 生产管控依赖设备数据，决策支持依赖生产管控与质量管理，
营销协同依赖生产管控）。若把 `depends_on` 当成路径库内部步号解释，这些依赖将全部指向不存在的步骤。

## 4. 参数表结构：为什么是 `paths` 和 `actions` 两张表

**核心发现：`path_ref` 不是参数表的主键。**

- `path_ref` ↔ 目标场景在 6 个样例间**完全稳定**（PATH-007 恒为 S07，PATH-010 恒为 S10，…）。
- 但同一个 `path_ref` 在不同样例下解析出**不同参数**：

| PATH | 出现样例 | 改造项 | 投入区间 | 弹性 |
|---|---|---|---|---|
| PATH-007 | ap0、ap4 | P-PLAN 规划、制度与数字化人才底座 | [10, 30] | 采集项 15：0.1%—0.3%（未支撑） |
| PATH-007 | ap2、ap3 | P-QC 质量数据闭环与在线管控上线 | [40, 120] | 采集项 13：1.5%—4%；采集项 15：0.5%—1.5% |
| PATH-010 | ap2 | P-PLAN 规划、制度与数字化人才底座 | [10, 30] | 采集项 15：0.1%—0.3%（未支撑） |
| PATH-010 | ap1、ap3、baseline | P-ENERGY 能耗在线监测与用能优化 | [20, 60] | 采集项 12：2%—5%；采集项 15：0.2%—0.8% |

- 真正稳定的参数主键是**改造项 `action_id`**（即 ranking 行的 `action_id`）：
  9 个改造项在 6 个样例之间的投入区间、弹性区间、依赖关系**完全一致，零冲突**。
  其中 P-PLAN 是「管理底座」通用条目，会被挂到不同场景的路径下（PATH-007 / PATH-010 / PATH-011），
  参数始终相同。

因此 `data/pathways.json` 给两张表：

| 表 | 主键 | 用途 |
|---|---|---|
| `paths` | PATH id（9 条） | 满足「路径级参数表」的原始诉求。路径级平铺字段（`target_scenario` / `action_name` / `cost_range` / `depends_on_paths` / `elasticity`）描述该路径的**主步骤**；`steps[]` 列出该路径下观测到的全部参数条目；多步骤路径带 `multi_step: true` |
| `actions` | 改造项 id（9 条） | 无冲突的参数表，**后端做 ROI 复算应当直接消费这张** |

主步骤的确定性选取规则（写在脚本里，可复现）：

1. 优先取「跨样例场景固定、且该场景等于本路径目标场景」的改造项（场景专属条目）；
2. 否则取观测样例最多的；
3. 再并列则按 `action_id` 字典序。

据此：PATH-007 主步骤 = P-QC，PATH-010 主步骤 = P-ENERGY，PATH-011 只有一个通用条目 P-PLAN。

`data/pathways.json` 另外记录了 `conflicts`（上述 2 处多参数路径）与 `consistency`（检查统计）。

## 8. 已知局限与遗留风险

1. **路径库不完整（最大缺口）**：6 个样例只触达 9 个 PATH id / 9 个改造项、9 个场景
   （S01、S03、S06、S07、S08、S09、S10、S11、S16）。`precomputed/scenario_judgments.json` 覆盖 S01—S16，
   其余 7 个场景（S02、S04、S05、S12、S13、S14、S15）的路径与弹性在样例里**没有任何观测，无法还原**，
   必须由论文库 / 案例库补口径或人工补录。
2. **PATH 编号不完整**：观测到 PATH-001 / 003 / 006 / 007 / 008 / 009 / 010 / 011 / 014，
   中间号段（002、004、005、012、013、015、016）未出现在任何样例里，
   无法判断这些路径是否存在、对应哪个场景。
3. **PATH 编号不是场景号**：PATH-014 对应的是 S16 而不是 S14，说明 `path_ref` 是手工编号，
   不可由场景号反推路径号。
4. **营收缩放律不可观测**：6 个样例的 `profile.revenue_wan` 全为 6000，
   而 `cost_basis` 写「按营收规模折算（参考 6000 万元营收）」。
   本表 `cost_range` 是 **6000 万元营收基准值**；接入真实企业时缩放律必须由人工确认，
   否则会给出偏高的收益-投入比。
5. **步骤序号是位置号，不是路径库内部步号**：6 个样例里 `step` 恒等于该步骤在 `pathway` 数组中的位置（1 起）。
   路径库内部的步号在落盘时已丢失，本文件不臆造，只按位置解释 `depends_on`（§3.4 已给出自洽性佐证）。
6. **P-SEC 没有成效条目**：采集项 12—15 一个都不挂，收益恒为 0、ROI 恒为 0。
   它参与排序（占位、提示仍要做合规整改），但不产生可量化收益。
7. **supported=false 的条目不可作结论数**：仅 P-PLAN 的采集项 15（0.1%—0.3%）属此类，
   样例文案明确写「只用于排序，不作为结论数」。本表原样保留该标记。
8. **弹性本身是演示估算**：样例 `roi_assumptions.elasticity` 原文写
   「成效弹性为演示估算区间，无公开案例支撑，只用于排序，不作为结论数」。
   本表只是把既有估算搬进后端，**没有提升任何证据等级**。
9. **本文件是反解结果，不是新口径**：所有数字都来自预计算产物。
   人工调整必须同步改生成脚本，否则预计算样例与实时推理会分叉。
10. **敏感性与翻转数未还原**：`ranking[].sensitivity`（±40% 扰动下的排序翻转数）依赖生成脚本的
    蒙特卡洛流程，无法从落盘结果反解，本次未纳入参数表。
